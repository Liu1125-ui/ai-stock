# 日常启动修复设计与计划

目标：解决 Docker Desktop 同时启动容器时，业务服务早于 Nacos 就绪而退出的问题。新增根目录双击入口，日常运行不重新构建、不拉取镜像、不创建容器、不初始化配置。

实施：先验证原项目十个容器身份；按 MySQL/Nacos/算法、五业务服务、网关、前端的顺序启动，分别等待数据库健康、Nacos HTTP 与 gRPC 就绪、应用健康和页面可访问。已有健康服务不重启。等待有总时限，退出的应用仅重启一次；失败指明服务并停止后续步骤。保留已有环境变量、数据卷和后台任务开关。

验证：先用隔离桩验证顺序、依赖失败阻断和身份校验，再验证原部署启动及重复执行。不得调用 AI、发送邮件或更改业务数据来验收。旧构建脚本保留，仅用于开发部署。

## 验证记录

隔离测试通过：依赖顺序、依赖失败阻断、容器标签身份、JSON/HTML字节响应、挂起子进程超时及非零退出。已观察到PowerShell返回字节数组的真实兼容问题，修复后回归通过。独立审查指出同步Docker命令可能挂起，已统一封装30秒超时并复审通过。

等待上限：Docker引擎就绪预算120秒；服务就绪预算默认600秒；每个Docker命令另有30秒上限，探针3秒，实际结束可略超预算。失败不清理数据或重建环境。Docker Desktop中直接点击项目Start不能保证依赖顺序，请使用新入口。

真实部署验收：十个原容器完整停止后，新入口按顺序冷启动成功；MySQL/Nacos健康，算法、五业务服务、网关健康，前端/login可访问。原容器ID、Config.Env与Mounts的内存SHA-256摘要前后一致；不输出环境变量正文。再次运行启动器成功，十容器StartedAt均未改变。专用测试数据库未启动。仅做启动与只读健康探测，未主动调用AI或发送邮件。
